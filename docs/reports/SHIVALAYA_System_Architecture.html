01 · System Overview

The Complete System Map

One Supabase database is the single source of truth. Three web apps connect to it. All state changes propagate in real-time via WebSockets. No app talks to another directly — everything goes through the database.

02 · Applications

The Three Apps — Roles & Responsibilities

Each app has a clearly separated role. No app handles another's domain. All share the same Supabase backend.

App 1 Shivalaya Guest Portal

order.shivalayaresorts.com

Mobile-first. Accessed via QR scan by resort guests. Contains the landing page, full food ordering system, real-time order tracking, and the complete activities & experiences booking module.


Writes to: orders, order_items, activity_bookings

Reads from: menu_items, menu_categories, activities, activity_time_slots, activity_bookings (own), orders (own)

Subscribes: orders channel (own order status updates)

App 2 Panache Kitchen Panel

kitchen.shivalayaresorts.com

Desktop/tablet. Used exclusively by kitchen staff and restaurant servers. Handles food orders only — no activities, no guest management. Focused and distraction-free.


Writes to: orders (status only), order_status_log

Reads from: orders, staff

Subscribes: orders channel (all new orders, status changes)

App 3 Shivalaya Resort Reception

reception.shivalayaresorts.com

Desktop. Lives at the main resort reception counter. Handles guest check-in/out, activities confirmation and staff assignment, consolidated guest folio, analytics, menu management, and WhatsApp triggers.


Writes to: guests, activity_bookings (status), orders (manual), activities, activity_time_slots

Reads from: Everything — full access

Subscribes: activity_bookings channel, orders overview channel

04 · Real-time

Supabase Realtime Channels

Supabase Realtime wraps PostgreSQL's LISTEN/NOTIFY into WebSocket channels. Apps subscribe to specific channels and receive events within <200ms of a database change — no polling, no refresh.

Channel: orders

Who subscribes:

• Kitchen Panel subscribes to ALL new orders (service = any)

• Guest Portal subscribes FILTERED by order_id after placing order


Events emitted: INSERT (new order), UPDATE (status change)

Kitchen filter: status=eq.new

Guest filter: id=eq.[orderUUID]

Channel: activity_bookings

Who subscribes:

• Resort Reception subscribes to ALL new bookings and status changes

• Guest Portal subscribes FILTERED by booking_id for tracking


Events emitted: INSERT (new booking), UPDATE (confirmed/cancelled)

Reception shows: alert badge when new pending booking arrives

JavaScript Supabase Realtime subscription — Kitchen Panel 
// Kitchen Panel — subscribe to all new food orders in real-time
const channel = supabase
  .channel('kitchen_orders')
  .on(
    'postgres_changes',
    {
      event: '*',           // INSERT + UPDATE
      schema: 'public',
      table: 'orders',
      filter: `resort_id=eq.${resortId}`
    },
    (payload) => {
      if (payload.eventType === 'INSERT') {
        playNotificationSound();
        addOrderToQueue(payload.new);
        updateBadgeCount();
      }
      if (payload.eventType === 'UPDATE') {
        updateOrderStatus(payload.new.id, payload.new.status);
      }
    }
  )
  .subscribe();

// Guest Portal — track a specific order after placing it
const trackChannel = supabase
  .channel(`order_track_${orderId}`)
  .on(
    'postgres_changes',
    {
      event: 'UPDATE',
      schema: 'public',
      table: 'orders',
      filter: `id=eq.${orderId}`  // Only this order
    },
    (payload) => {
      updateTrackingUI(payload.new.status); // Updates tracker in <200ms
    }
  )
  .subscribe();
05 · Core Flow

Food Ordering — Complete Flow

Every step from QR scan to food served. Each step lists what happens in the frontend, what database operation fires, and what real-time event it triggers.

1

Guest Scans QR Code

QR encodes order.shivalayaresorts.com?room=302 or ?table=5&type=dine_in. Browser opens. Landing page renders.

Frontend reads URL params. If room=302 is present, it's stored in sessionStorage to pre-fill the checkout form.

NO DB read yet — landing page is static
2

Guest Taps "Order Food" → Menu Loads

Supabase JS client fetches all available items. Query applies two filters: is_available=true on menu_items AND time-gate check on menu_categories.

READ: menu_categories JOIN menu_items WHERE is_available=true AND current_time BETWEEN available_from AND available_until
3

Guest Builds Cart

Cart state is entirely in-memory (Zustand store). No DB writes during browsing. If an item has variants, a modal forces selection before the item is added. Cart renders as floating bottom bar.

If item has has_variants=true, client fetches that item's variants on-demand (menu_item_variants WHERE item_id=X).

READ: menu_item_variants (only on items with has_variants=true)
4

Guest Submits Checkout Form

Guest enters name, phone, room number (or table), service type, notes. Frontend validates all required fields. On submit, calls a Supabase RPC function (not a direct INSERT) to atomically create the order and generate the order number.

WRITE: INSERT orders + INSERT order_items (via RPC: create_order)
5

Order Created — Realtime Fires

Supabase Realtime broadcasts the INSERT event on the orders channel. The Kitchen Panel — which is always subscribed — receives the event within <200ms. The new order card appears at the top of the "New" column. Browser notification sound plays.

Guest Portal receives the order UUID back from the RPC call. It navigates to /order/PAN-00123 (the tracking page) and subscribes to real-time updates for that specific order.

REALTIME EVENT → Kitchen Panel: new order in queue ⚡
6

Kitchen Accepts Order

Kitchen staff clicks "Accept." Frontend calls UPDATE orders SET status='confirmed'. The order_status_log trigger fires (see below), writing an audit row automatically.

Guest's tracking page receives the UPDATE event via WebSocket. The tracker UI moves from "Received" to "Confirmed" — live, on the guest's phone.

WRITE: UPDATE orders SET status='confirmed' → TRIGGER: log_status_change → INSERT order_status_log
7

Kitchen Marks Ready → Guest Sees It

Kitchen updates status to 'ready'. Guest's phone shows the tracker jump to "Ready" in real-time. If dining in, the waiter calls the name. If room service, it's already on its way.

WRITE: UPDATE status='ready' → REALTIME to Guest Portal tracker ⚡
8

Order Marked Served — Folio Updated

Waiter clicks "Served." Status → 'served'. The order is now final. The guest's folio (SQL VIEW) automatically includes this charge under their room/stay. No separate step needed — the folio VIEW queries in real-time.

WRITE: UPDATE status='served' → guest_folio VIEW auto-includes this order
SQL Auto-trigger: log every status change + update updated_at 
CREATE OR REPLACE FUNCTION log_order_status_change()
RETURNS TRIGGER AS $$
BEGIN
  -- Only fire when status actually changes
  IF OLD.status != NEW.status THEN
    INSERT INTO order_status_log (
      order_id, old_status, new_status, changed_at
    ) VALUES (
      NEW.id, OLD.status, NEW.status, now()
    );
  END IF;

  -- Always update updated_at
  NEW.updated_at := now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER orders_status_log
  BEFORE UPDATE ON orders
  FOR EACH ROW
  EXECUTE FUNCTION log_order_status_change();
06 · Time Slot System — Schema Design

How the Time Slot System Is Modelled

The slot system separates the definition of a slot (when it repeats, what days, what capacity) from an individual booking (a specific guest, on a specific date). This lets you define a slot once and it recurs automatically every applicable day.

💡

The Key Design Decision

A time slot in activity_time_slots is a template — it says "Bird Cage Morning Session runs 7:00–9:00 AM every day." An activity_booking is the instance — it says "Guest Rajesh booked the Bird Cage Morning Session for August 12." The availability calculation always queries the bookings table for a specific (slot_id + booking_date) combination.

07 · Time Slot System — Customer Side

What the Guest Experiences

The booking flow is designed to be fully self-service. A guest who has never used the app before should be able to book an activity in under 60 seconds.

1

Guest Opens /experiences

The page loads all available activities with a single query. Only activities where is_available=true appear. Cards show name, short description, pricing structure, duration, and a "Book Now" button.

If the guest's room number is in session (from QR scan), it's stored in context — will be used to pre-fill the booking form.

READ: SELECT * FROM activities WHERE is_available=true ORDER BY sort_order
2

Guest Taps an Activity

Opens the activity detail page. The system immediately fetches available slots for today + the next 3 days. This calls the RPC function get_available_slots which returns each slot with its remaining capacity for the selected date.

Date chips appear at top (Today, Tomorrow, Date+2, Date+3). Time slot chips appear below — green for available with spots remaining, grey/strikethrough for full.

RPC: get_available_slots(activity_id, date) → returns slots with remaining capacity
3

Guest Selects Date + Time Slot

When guest taps a date chip, the time slots reload for that date. When a slot is tapped, it highlights. A "Continues" button appears. If they select a full slot, the UI shows "This slot is full — please pick another."

Each slot chip shows: label, time range, and a compact capacity indicator like "3 spots left" or "Full." For per_setup activities, capacity means how many simultaneous setups are available, not people.

4

Guest Fills Booking Form

Form appears below the slot picker (or as a bottom sheet on mobile). Fields:

• Number of guests (integer — affects total price for per_person activities)

• Name, Phone (pre-filled from session if available)

• Room number (pre-filled from QR session if scanned from room)

• Special requests (optional textarea)

Total price auto-calculates as guest changes the guest count: total = price_per_person × number_of_guests. For per_setup, total is always the fixed setup price regardless of guest count.

5

Guest Taps "Confirm Booking"

This calls the book_activity_slot RPC function (NOT a direct INSERT — the RPC handles concurrency locking). The function either succeeds and returns a booking_id, or fails with an error code.

If it fails (slot just filled while they were on the form — race condition): frontend shows "Sorry, this slot just filled up. Please select another time." The slot picker reloads with updated availability.

If it succeeds: confirmation screen appears immediately.

RPC: book_activity_slot(activity_id, slot_id, date, guests, name, phone, room, requests)
6

Confirmation Screen

Guest sees a confirmation card with booking reference (EXP-XXXXX), activity name, date, time slot, number of guests, total amount, and a note: "Our team will confirm this booking and any instructions will be shared shortly. Payment will be added to your room bill at checkout."

Status shows "Pending Confirmation" (brass/amber color). Once reception confirms in their dashboard, the status updates to "Confirmed" — guest can see this on their "My Bookings" page.

REALTIME: activity_bookings channel → Reception Dashboard notified ⚡
08 · Time Slot System — Backend Deep Dive

How Availability Is Calculated

Availability is not stored — it's computed on every request by counting existing non-cancelled bookings against the slot's max capacity. This means it's always accurate.

SQL RPC: get_available_slots — called when guest opens an activity detail page 
CREATE OR REPLACE FUNCTION get_available_slots(
  p_activity_id  UUID,
  p_date         DATE
)
RETURNS TABLE (
  slot_id              UUID,
  label                TEXT,
  start_time           TIME,
  end_time             TIME,
  max_capacity         INTEGER,
  booked_count         INTEGER,
  remaining_capacity   INTEGER,
  is_available         BOOLEAN
)
LANGUAGE plpgsql AS $$
BEGIN
  RETURN QUERY
    SELECT
      ats.id                        AS slot_id,
      ats.label,
      ats.start_time,
      ats.end_time,

      -- Effective max: slot override wins, else activity default
      COALESCE(ats.max_capacity_override, a.max_capacity_per_slot) AS max_capacity,

      -- Current bookings: SUM of number_of_guests (NOT count of rows!)
      -- Because 1 booking can cover 3 people
      COALESCE(
        (
          SELECT SUM(ab.number_of_guests)
          FROM activity_bookings ab
          WHERE
            ab.slot_id = ats.id
            AND ab.booking_date = p_date
            AND ab.status NOT IN ('cancelled', 'no_show')
        ),
        0
      ) AS booked_count,

      -- Remaining = max - booked
      COALESCE(ats.max_capacity_override, a.max_capacity_per_slot)
        - COALESCE(
            (SELECT SUM(ab.number_of_guests)
             FROM activity_bookings ab
             WHERE ab.slot_id = ats.id
               AND ab.booking_date = p_date
               AND ab.status NOT IN ('cancelled', 'no_show')),
            0
          )
      AS remaining_capacity,

      -- is_available: slot is active AND has remaining capacity
      -- AND the slot day matches the requested date's day of week
      (
        ats.is_active = TRUE
        AND a.is_available = TRUE
        AND EXTRACT(DOW FROM p_date) = ANY(ats.days_available)
        AND (
          COALESCE(ats.max_capacity_override, a.max_capacity_per_slot)
          - COALESCE(
              (SELECT SUM(number_of_guests)
               FROM activity_bookings
               WHERE slot_id = ats.id
                 AND booking_date = p_date
                 AND status NOT IN ('cancelled', 'no_show')),
              0
            )
        ) > 0
        -- Enforce minimum advance booking hours
        AND (
          p_date > CURRENT_DATE
          OR (
            p_date = CURRENT_DATE
            AND (ats.start_time - make_interval(hours => a.min_advance_hours)) > CURRENT_TIME
          )
        )
      ) AS is_available

    FROM activity_time_slots ats
    JOIN activities a ON ats.activity_id = a.id

    WHERE
      ats.activity_id = p_activity_id
      AND EXTRACT(DOW FROM p_date) = ANY(ats.days_available)

    ORDER BY ats.sort_order, ats.start_time;
END;
$$;
⚠️

Important: Counting guests, not bookings

The availability query uses SUM(number_of_guests), not COUNT(*). This is critical. If Bird Cage has max capacity 6 and one booking is for 4 people, only 2 spots remain — not 5. Counting rows instead of people would overbook the slot.

09 · Time Slot System — Concurrency Control

Preventing Double-Booking

Two guests could tap "Confirm" on the last available spot at the same millisecond. Without locking, both would succeed and overbook the slot. The solution is PostgreSQL advisory locks inside a transaction.

🔒

How advisory locks work

pg_advisory_xact_lock(key) acquires a session-level lock on an integer key. Any other transaction trying to acquire the same key will wait until the first transaction commits or rolls back. The key is derived from a hash of slot_id + booking_date — so only concurrent bookings for the exact same slot on the same day compete for the lock. Different slots never block each other.

SQL RPC: book_activity_slot — the atomic, concurrency-safe booking function 
CREATE OR REPLACE FUNCTION book_activity_slot(
  p_activity_id     UUID,
  p_slot_id         UUID,
  p_booking_date    DATE,
  p_number_guests   INTEGER,
  p_guest_name      TEXT,
  p_guest_phone     TEXT,
  p_room_number     TEXT,
  p_special_requests TEXT DEFAULT NULL
)
RETURNS JSONB   -- Returns {success, booking_id, booking_number} or {success, error}
LANGUAGE plpgsql AS $$
DECLARE
  v_max_capacity    INTEGER;
  v_booked_count    INTEGER;
  v_remaining       INTEGER;
  v_pricing_type    TEXT;
  v_unit_price      INTEGER;
  v_total_amount    INTEGER;
  v_booking_id      UUID;
  v_booking_number  TEXT;
  v_lock_key        BIGINT;
  v_room_id         UUID;
  v_guest_id        UUID;
BEGIN

  -- ① DERIVE ADVISORY LOCK KEY from slot+date combination
  -- hashtext returns an integer — unique per slot+date pair
  v_lock_key := hashtext(p_slot_id::text || p_booking_date::text);

  -- ② ACQUIRE LOCK — blocks until acquired (auto-released on tx end)
  PERFORM pg_advisory_xact_lock(v_lock_key);

  -- ③ GET ACTIVITY DETAILS (pricing, capacity)
  SELECT
    COALESCE(ats.max_capacity_override, a.max_capacity_per_slot),
    a.pricing_type,
    CASE a.pricing_type
      WHEN 'per_person'  THEN a.price_per_person
      WHEN 'per_setup'   THEN a.price_per_setup
      WHEN 'per_session' THEN a.price_per_session
    END
  INTO v_max_capacity, v_pricing_type, v_unit_price
  FROM activity_time_slots ats
  JOIN activities a ON ats.activity_id = a.id
  WHERE ats.id = p_slot_id;

  -- ④ COUNT EXISTING BOOKINGS (after lock — no race condition possible)
  SELECT COALESCE(SUM(number_of_guests), 0)
  INTO v_booked_count
  FROM activity_bookings
  WHERE
    slot_id = p_slot_id
    AND booking_date = p_booking_date
    AND status NOT IN ('cancelled', 'no_show');

  v_remaining := v_max_capacity - v_booked_count;

  -- ⑤ CAPACITY CHECK
  IF p_number_guests > v_remaining THEN
    RETURN jsonb_build_object(
      'success', false,
      'error', 'SLOT_FULL',
      'remaining', v_remaining,
      'message', 'This slot is fully booked. Please choose another time.'
    );
  END IF;

  -- ⑥ CALCULATE TOTAL AMOUNT
  v_total_amount := CASE v_pricing_type
    WHEN 'per_person'  THEN v_unit_price * p_number_guests
    WHEN 'per_setup'   THEN v_unit_price  -- always fixed
    WHEN 'per_session' THEN v_unit_price  -- always fixed
  END;

  -- ⑦ RESOLVE room_id from room_number (if provided)
  IF p_room_number IS NOT NULL THEN
    SELECT id, current_guest_id
    INTO v_room_id, v_guest_id
    FROM rooms
    WHERE room_number = p_room_number;
  END IF;

  -- ⑧ GENERATE BOOKING NUMBER
  v_booking_number := 'EXP-' || to_char(
    nextval('booking_number_seq'), 'FM00000'
  );

  -- ⑨ INSERT THE BOOKING (capacity confirmed, lock held)
  INSERT INTO activity_bookings (
    booking_number, activity_id, slot_id, booking_date,
    guest_id, room_id,
    guest_name, guest_phone,
    number_of_guests,
    pricing_type_snapshot, unit_price_snapshot, total_amount,
    status, special_requests
  ) VALUES (
    v_booking_number, p_activity_id, p_slot_id, p_booking_date,
    v_guest_id, v_room_id,
    p_guest_name, p_guest_phone,
    p_number_guests,
    v_pricing_type, v_unit_price, v_total_amount,
    'pending', p_special_requests
  )
  RETURNING id INTO v_booking_id;

  -- Lock auto-released when transaction commits

  RETURN jsonb_build_object(
    'success', true,
    'booking_id', v_booking_id,
    'booking_number', v_booking_number,
    'total_amount', v_total_amount
  );

EXCEPTION WHEN OTHERS THEN
  RETURN jsonb_build_object(
    'success', false,
    'error', 'SERVER_ERROR',
    'message', SQLERRM
  );
END;
$$;
✅

Why this is race-condition proof

Between steps ② and ⑨, no other booking for the same slot+date can run. The advisory lock is held for the entire transaction. Step ④ runs AFTER the lock, so the count it reads is the true committed count. Even if 50 guests all tap "Confirm" simultaneously, they queue up at step ② and each one either books successfully or gets SLOT_FULL — no double booking possible.

How Reception Manages Bookings

The Resort Reception dashboard is the control center for all activity bookings. From here, the owner or reception staff confirms, assigns staff, and marks activities complete.

1

New Booking Notification Arrives

The Reception Dashboard's WebSocket subscription receives this immediately. A notification badge appears on the "Activity Bookings" section tab, a soft chime plays, and the booking card appears at the top of the "Pending" list.

2

Reception Reviews the Booking

The booking card shows: Activity name, date, time slot, number of guests, room number, guest name, special requests, and total amount (already calculated). Reception also sees the notes_for_staff from the activity configuration (e.g., "Bird Cage: ensure morning feed is prepared before 6:45 AM").

Reception can check the calendar view to see if any guides/staff are already committed to another slot at the same time.

3

Reception Confirms + Assigns Staff

Two actions in one panel: Reception types the staff member's name in "Assign to" (e.g., "Ramesh — Bird Cage Guide") and any instructions (e.g., "Meet guest at garden gate at 7:00 AM"). Then clicks Confirm.

This fires: UPDATE activity_bookings SET status='confirmed', assigned_staff_name='Ramesh', staff_instructions='...', confirmed_by=[staff_id].

The Guest Portal tracking page — if open — receives the UPDATE event and changes the booking status from "Pending Confirmation" to "Confirmed ✓".

WRITE: UPDATE activity_bookings SET status='confirmed' → REALTIME to Guest Portal ⚡
4

Day-of: Calendar View

On the day of the activity, the calendar view shows all confirmed bookings for today, ordered by time. Reception staff can brief their guides/activity coordinators from this view.

Each calendar block shows: Activity, Time, Room, Guest name, Guest count, Assigned staff, Instructions.

5

Activity Completed → Folio Updated

After the activity happens, reception marks it "Completed." This sets status='completed' on the booking. The guest_folio VIEW immediately reflects this charge under the guest's room for checkout billing.

If cancelled: status='cancelled', cancellation_reason required, amount = ₹0 on folio. The capacity is restored automatically — the availability query excludes cancelled bookings.

WRITE: UPDATE status='completed' → guest_folio VIEW auto-includes ✓
Owner Configuration Panel
Adding a New Activity

Reception section → Activity Management → "Add Activity." Form with all fields from the activities table. On save: INSERT activities, then owner adds time slots via the slot builder (visual time picker + days checkboxes + capacity input).

The activity appears on the Guest Portal immediately on next page load (or real-time if the portal polls activities every 60 seconds).

Check-in → Supabase → WhatsApp

Check-in is the moment a guest becomes "known" to the system. After this, all their orders and activity bookings are automatically linked to their room, building the folio in real-time through their stay.

Reception Opens Check-In Panel

• UPDATE rooms SET is_occupied=true, current_guest_id=[new_guest_id]

WRITE: INSERT guests + UPDATE rooms (atomic transaction)

The INSERT on guests fires a PostgreSQL trigger on_guest_checkin. This trigger calls a Supabase Edge Function via pg_net (Supabase's built-in HTTP from within Postgres). The Edge Function receives the guest data.

Edge Function → WhatsApp API

The Edge Function receives: guest_name, phone, room_number, resort_name. It calls the AiSensy/Interakt API with the pre-approved check-in template, substituting the variables. The WhatsApp message lands on the guest's phone within ~15 seconds of check-in.

The Edge Function then writes to whatsapp_log: provider_message_id, status='sent', sent_at.

HTTP POST → AiSensy API → Guest's WhatsApp within ~15 seconds
5

Guest Receives Welcome Message

The WhatsApp message contains the welcome text, the guest portal URL (order.shivalayaresorts.com), and instructions to scan the QR code in their room. From this moment, if they order food or book activities using their room number, those charges automatically link to guest_id via the room lookup.

TypeScript Supabase Edge Function: send-checkin-whatsapp 
// supabase/functions/send-checkin-whatsapp/index.ts
import { serve } from 'https://deno.land/std/http/server.ts'

serve(async (req) => {
  const { guest_name, guest_phone, room_number } = await req.json();

  // Call AiSensy API
  const response = await fetch('https://backend.aisensy.com/campaign/t1/api/v2', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({
      apiKey: Deno.env.get('AISENSY_API_KEY'),
      campaignName: 'guest_checkin_v1',          // Approved template name
      destination: guest_phone,                        // E.164: +919876543210
      userName: 'Shivalaya Resorts',
      templateParams: [
        guest_name,                                    // {{1}} in template
        room_number,                                   // {{2}} in template
        'https://order.shivalayaresorts.com'           // {{3}} in template
      ]
    })
  });

  const result = await response.json();

  // Log to whatsapp_log table
  const { createClient } = await import('https://esm.sh/@supabase/supabase-js@2');
  const supabase = createClient(
    Deno.env.get('SUPABASE_URL')!,
    Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!
  );

  await supabase.from('whatsapp_log').insert({
    guest_phone,
    message_type: 'checkin',
    template_name: 'guest_checkin_v1',
    provider_message_id: result.messageId,
    status: response.ok ? 'sent' : 'failed',
    error_message: response.ok ? null : JSON.stringify(result)
  });

  return new Response(JSON.stringify({ ok: response.ok }));
});
12 · Guest Folio System

Consolidated Billing — How the Folio Works

The guest folio is not a stored table — it's a live SQL VIEW that queries both orders and activity_bookings for a given guest's stay, ordered chronologically. Whenever a new order is placed or activity is completed, the folio automatically reflects it.

SQL guest_folio VIEW — the unified billing view 
CREATE OR REPLACE VIEW guest_folio AS

  -- Food orders
  SELECT
    o.id,
    o.guest_id,
    o.room_id,
    o.created_at                    AS charge_at,
    'food'                          AS charge_type,
    o.order_number                  AS reference_number,
    'Food Order — Panache Restaurant' AS description,
    o.items                         AS line_items,   -- jsonb
    o.subtotal                      AS amount,
    o.status,
    o.service_type                  AS detail

  FROM orders o
  WHERE o.status NOT IN ('cancelled')

  UNION ALL

  -- Activity bookings
  SELECT
    ab.id,
    ab.guest_id,
    ab.room_id,
    ab.created_at                   AS charge_at,
    'activity'                      AS charge_type,
    ab.booking_number               AS reference_number,
    a.name || ' — ' ||
      to_char(ab.booking_date, 'DD Mon') || ', ' ||
      to_char(ats.start_time, 'HH12:MI AM')
                                    AS description,
    NULL                            AS line_items,
    ab.total_amount                 AS amount,
    ab.status,
    ab.pricing_type_snapshot || ': ' ||
      ab.number_of_guests::text || ' guest(s)'
                                    AS detail

  FROM activity_bookings ab
  JOIN activities a        ON ab.activity_id = a.id
  JOIN activity_time_slots ats ON ab.slot_id = ats.id
  WHERE ab.status NOT IN ('cancelled')

ORDER BY charge_at;
SQL Querying the folio for a specific guest at checkout 
-- Get everything billed to guest_id during their stay
SELECT
  charge_type,
  reference_number,
  description,
  line_items,
  amount,
  status,
  charge_at

FROM guest_folio
WHERE
  guest_id = '[guest-uuid]'
  AND charge_at >= '2026-08-10'  -- check-in date
  AND charge_at <  '2026-08-13'  -- checkout date

ORDER BY charge_at;

SQL Row Level Security — orders table policies 
-- Enable RLS on orders table
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- Kitchen staff: can read all orders for their resort, update status only
CREATE POLICY kitchen_read_orders ON orders
  FOR SELECT TO authenticated
  USING (
    resort_id = (SELECT resort_id FROM staff
                 WHERE supabase_user_id = auth.uid()
                 AND role = 'kitchen')
  );

CREATE POLICY kitchen_update_status ON orders
  FOR UPDATE TO authenticated
  USING (resort_id = (SELECT resort_id FROM staff
                       WHERE supabase_user_id = auth.uid()))
  WITH CHECK (
    -- Kitchen can only change status field, nothing else
    status IN ('confirmed', 'preparing', 'ready', 'served')
  );

-- Guests: anon users can INSERT orders and read their own
CREATE POLICY guest_insert_order ON orders
  FOR INSERT TO anon
  WITH CHECK (true);  -- RPC function validates room/guest matching

  FOR SELECT TO anon
