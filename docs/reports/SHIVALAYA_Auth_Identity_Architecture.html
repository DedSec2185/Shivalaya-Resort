01 · Authentication

User Types — Who Can Access What

There are exactly four identity types in the system. Three have Supabase Auth accounts. One — the guest — has no account at all. Understanding this separation is the foundation of every security decision.

Identity TypeAuth MethodAccount Exists?Created BySession LengthCan Do
Guest (Anon) No login. Room number + phone = identity. No Supabase Auth account N/A — Supabase anon key Browser session only Browse menu, place orders, book activities, track own order
Kitchen Staff Profile select + 4-digit PIN → Supabase Auth signIn Yes — auth.users + staff table Owner via Reception dashboard 12 hours (auto-logout) View/update food orders only
Receptionist Email + 6-digit PIN → Supabase Auth signIn Yes — auth.users + staff table Owner via Reception dashboard 8 hours Guest check-in/out, activity confirmation, folio view
Owner Email + strong password → Supabase Auth signIn Yes — auth.users + staff table ASVEX Technologies (one-time setup) 24 hours Full access — all data, settings, analytics, staff management
🔑

Critical Design Decision: Guests Never Have Accounts

A guest ordering food at 2 AM should not have to create an account, remember a password, or verify an email. Their room number is their identity for the duration of their stay. Supabase's anonymous session (using the anon key) handles their API access, while RLS policies strictly limit what anonymous sessions can read and write. The guest record in the guests table is created by the receptionist at check-in — not by the guest themselves.

01 · Authentication

Owner Account Creation

This happens exactly once, performed by ASVEX during initial platform setup. The owner account has the highest privilege level and is never created via the app's own UI — only via the Supabase Admin API using the service role key.

Step-by-Step: Creating the Owner Account

1

ASVEX creates auth.users entry via Admin API

Using the Supabase service role key (never exposed to browser), ASVEX calls the Admin API to create the Supabase Auth user. The email becomes the owner's login identity permanently.

TypeScriptRun once — initial setup script
// supabase/scripts/create-owner.ts — ASVEX runs this once
import { createClient } from '@supabase/supabase-js'

const supabaseAdmin = createClient(
  process.env.SUPABASE_URL!,
  process.env.SUPABASE_SERVICE_ROLE_KEY!  // Admin key — never in browser
)

async function createOwnerAccount() {
  // Step 1: Create Supabase Auth user
  const { data: authUser, error: authError } =
    await supabaseAdmin.auth.admin.createUser({
      email:         'vikas@shivalayaresorts.com',
      password:      '[strong-random-32-char-password]',
      email_confirm: true,       // Skip email verification
      user_metadata: { name: 'Vikas Dubey', role: 'owner' }
    })

  if (authError) throw authError
  console.log('Auth user created:', authUser.user.id)

  // Step 2: Get resort ID from resorts table
  const { data: resort } = await supabaseAdmin
    .from('resorts').select('id').eq('slug', 'shivalaya-resorts').single()

  // Step 3: Create corresponding staff record
  const { error: staffError } = await supabaseAdmin
    .from('staff')
    .insert({
      resort_id:        resort.id,
      supabase_user_id: authUser.user.id,
      name:             'Vikas Dubey',
      role:             'owner',
      is_active:        true,
      pin_hash:         null  // Owner uses password, not PIN
    })

  if (staffError) throw staffError
  console.log('Owner setup complete. Auth ID:', authUser.user.id)
}

2

Password policy and delivery

The initial password is generated as a cryptographically random 32-character string (letters, numbers, symbols). It is delivered to the owner via a secure channel — a password manager shared link or encrypted WhatsApp message. The owner changes it on first login.

Password requirements enforced at Supabase Auth level: minimum 12 characters, at least one number, one symbol. No maximum limit.

Staff Account Creation — Owner Creates via Reception

After the owner account exists, all other staff accounts (receptionist, kitchen) are created by the owner through the Reception dashboard's Staff Management panel. This never requires ASVEX involvement for day-to-day staff changes.

How the Owner Creates a New Staff Member

1

Owner opens Staff Management in Reception → "Add Staff"

Form fields: Staff Name, Role (kitchen/receptionist), PIN (4-digit for kitchen, 6-digit for receptionist). The email is auto-generated as [name-slug]@staff.shivalayaresorts.com — the staff member never sees this email, it's just a technical identifier.

2

Frontend calls the create_staff_account RPC (SECURITY DEFINER)

This RPC runs with elevated privileges (SECURITY DEFINER) so it can call the Supabase Admin API functions — which anonymous or regular authenticated sessions cannot do. The owner's session is authenticated, but the Admin API call itself uses the service role.

SQLcreate_staff_account RPC — callable only by owner role
CREATE OR REPLACE FUNCTION create_staff_account(
  p_resort_id  UUID,
  p_name       TEXT,
  p_role       TEXT,  -- 'kitchen' | 'receptionist'
  p_pin        TEXT   -- raw PIN (e.g. '2847')
)
RETURNS JSONB LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE
  v_email       TEXT;
  v_password    TEXT;
  v_auth_result JSONB;
  v_auth_uid    UUID;
  v_staff_id    UUID;
BEGIN
  -- Guard: only owner can create staff
  IF NOT EXISTS (
    SELECT 1 FROM staff
    WHERE supabase_user_id = auth.uid()
      AND role = 'owner'
      AND resort_id = p_resort_id
  ) THEN
    RAISE EXCEPTION 'Unauthorized: only owner can create staff';
  END IF;

  -- Generate system email and strong password
  v_email    := lower(regexp_replace(p_name, '\s+', '-', 'g'))
                || '@staff.shivalayaresorts.com';
  v_password := encode(gen_random_bytes(24), 'hex'); -- 48-char hex

  -- Call Supabase Admin API via pg_net (HTTP from inside Postgres)
  SELECT content::jsonb INTO v_auth_result
  FROM net.http_post(
    url     := current_setting('app.edge_function_base_url') || '/create-staff-auth',
    headers := jsonb_build_object(
      'Authorization', 'Bearer ' || current_setting('app.service_role_key'),
      'Content-Type',  'application/json'
    ),
    body := jsonb_build_object(
      'email',    v_email,
      'password', v_password,
      'name',     p_name,
      'role',     p_role
    )
  );

  v_auth_uid := (v_auth_result->>'user_id')::uuid;

  -- Store bcrypt-hashed PIN in staff table
  INSERT INTO staff(
    resort_id, supabase_user_id, name, role,
    pin_hash, supabase_system_email, is_active
  ) VALUES(
    p_resort_id, v_auth_uid, p_name, p_role,
    crypt(p_pin, gen_salt('bf', 12)),  -- bcrypt work factor 12
    v_email, true
  ) RETURNING id INTO v_staff_id;

  -- Log the account creation
  INSERT INTO auth_audit_log(
    event_type, actor_id, target_id, metadata
  ) VALUES(
    'staff_account_created',
    auth.uid(),
    v_auth_uid,
    jsonb_build_object('name', p_name, 'role', p_role)
  );

  RETURN jsonb_build_object(
    'success', true,
    'staff_id', v_staff_id,
    'name',     p_name
  );
END;
$$;
DB WRITE: auth.users (via Edge Function) + staff table + auth_audit_log
3

The create-staff-auth Edge Function (called by the RPC)

This Deno function receives the staff details and uses the Supabase Admin API to create the auth user — something only possible with the service role key, kept exclusively server-side.

TypeScriptsupabase/functions/create-staff-auth/index.ts
import { serve } from 'https://deno.land/std/http/server.ts'
import { createClient } from 'https://esm.sh/@supabase/supabase-js@2'

serve(async (req) => {
  // Verify the call came from our own DB trigger/RPC
  const token = req.headers.get('Authorization')?.split(' ')[1]
  if (token !== Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')) {
    return new Response('Unauthorized', { status: 401 })
  }

  const { email, password, name, role } = await req.json()

  const admin = createClient(
    Deno.env.get('SUPABASE_URL')!,
    Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!
  )

  const { data, error } = await admin.auth.admin.createUser({
    email,
    password,
    email_confirm: true,   // Staff never see or use email directly
    user_metadata: { name, role, created_by: 'owner' }
  })

  if (error) return new Response(
    JSON.stringify({ error: error.message }), { status: 400 }
  )

  return new Response(
    JSON.stringify({ user_id: data.user.id })
  )
})

TypeScriptPIN attempt tracking with lockout
const LOCKOUT_AFTER_ATTEMPTS = 3
const LOCKOUT_DURATION_MS    = 30_000   // 30 seconds

interface PinAttemptState {
  staffId:    string
  attempts:   number
  lockedUntil: Date | null
}

const attemptStore = new Map<string, PinAttemptState>()

function checkLockout(staffId: string): boolean {
  const state = attemptStore.get(staffId)
  if (!state?.lockedUntil) return false
  if (Date.now() > state.lockedUntil.getTime()) {
    state.lockedUntil = null   // Lockout expired
    state.attempts    = 0
    return false
  }
  return true   // Still locked
}
3

PIN submitted → verify_staff_pin RPC (bcrypt comparison)

SQLverify_staff_pin — SECURITY DEFINER — reads pin_hash internally
CREATE OR REPLACE FUNCTION verify_staff_pin(
  p_staff_id UUID,
  p_pin      TEXT
)
RETURNS JSONB LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE
  v_staff staff%ROWTYPE;
BEGIN
  -- Fetch full staff record (SECURITY DEFINER bypasses RLS)
  SELECT * INTO v_staff
  FROM staff WHERE id = p_staff_id;

  IF NOT FOUND THEN
    RETURN jsonb_build_object('valid',false,'error','NOT_FOUND');
  END IF;

  IF NOT v_staff.is_active THEN
    RETURN jsonb_build_object('valid',false,'error','ACCOUNT_INACTIVE');
  END IF;

  -- bcrypt comparison: crypt(input_pin, stored_hash) must equal stored_hash
  -- bcrypt is self-salted — the salt is embedded in the hash string
  IF v_staff.pin_hash = crypt(p_pin, v_staff.pin_hash) THEN
    -- Log successful login
    INSERT INTO auth_audit_log(event_type, actor_id, metadata)
    VALUES('staff_pin_login_success', v_staff.supabase_user_id,
      jsonb_build_object('name', v_staff.name, 'role', v_staff.role));

    RETURN jsonb_build_object(
      'valid',              true,
      'staff_name',         v_staff.name,
      'role',              v_staff.role,
      'supabase_user_id',   v_staff.supabase_user_id::text,
      'system_email',       v_staff.supabase_system_email
    );
  ELSE
    -- Log failed attempt
    INSERT INTO auth_audit_log(event_type, actor_id, metadata)
    VALUES('staff_pin_login_failed', v_staff.supabase_user_id,
      jsonb_build_object('staff_id', p_staff_id));

    RETURN jsonb_build_object('valid',false,'error','INVALID_PIN');
  END IF;
END;
$$;
🔐

How bcrypt works here

bcrypt is a password-hashing algorithm that includes the salt inside the hash output. When the PIN "2847" is hashed with gen_salt('bf', 12), the result looks like: $2a$12$[22-char-salt][31-char-hash]. When verifying, crypt('2847', stored_hash) extracts the salt from the stored_hash, hashes the input with that same salt, and compares. This means even if the staff table is somehow leaked, attackers cannot reverse the PINs — bcrypt with work factor 12 takes ~300ms per attempt, making brute force of 10,000 possible 4-digit PINs take 50 minutes per hash.

4

Successful PIN → establish Supabase Auth session

The RPC returns the staff member's system_email. The frontend uses this with the system password (stored as env variable) to sign in via Supabase Auth. This establishes a real JWT session — required for RLS policies to grant kitchen access.

01 · Authentication

Guest Identity — No Account, No Login

Guests interact with the platform entirely without creating an account. Their identity is their room number and phone number — both of which are known because the receptionist entered them during check-in. The QR code begins the session, the room number links everything.

How Guests Access the API

All Guest Portal API calls use the Supabase anon key. This key is public — it's embedded in the JavaScript bundle. Security comes from RLS policies, not from keeping the key secret. Every anon session has identical minimal privileges. No anon session can read another guest's data.

What "Guest Identity" Actually Means

When a guest places an order, they submit their name, phone, and room number in the checkout form. The create_order RPC uses the room number to look up rooms.current_guest_id — linking the order to the checked-in guest record automatically. The guest doesn't authenticate; the room occupancy authenticates their identity.

02 · Room-Guest Binding

Data Model — How Rooms and Guests Connect

The binding between a guest and their room is maintained through two synchronized state pointers. Understanding both is essential to understanding how every order and activity booking gets attributed to the right guest.

SQLThe two-pointer system — rooms and guests cross-reference each other
┌─────────────────────────────────────┐    ┌──────────────────────────────────────┐
│            rooms                    │    │             guests                   │
├─────────────────────────────────────┤    ├──────────────────────────────────────┤
│ id               UUID PK            │    │ id               UUID PK             │
│ room_number      TEXT  '302'        │    │ room_id          UUID FK → rooms.id  │
│ is_occupied      BOOL  TRUE   ◄─┐   │    │ guest_name       TEXT  'Rajesh Kumar' │
│ current_guest_id UUID FK ──────┼──┐ │    │ guest_phone      TEXT  '9876543210'  │
└─────────────────────────────────┼──┼─┘   │ check_in_date    DATE  '2026-08-13' │
                                  │  │     │ expected_checkout DATE '2026-08-16'  │
                                  │  │     │ actual_checkout   TIMESTAMPTZ null   │
                                  │  └─────│ status           TEXT  'checked_in' │
                                  │        └──────────────────────────────────────┘
                                  │
                   current_guest_id is the LIVE POINTER.
                   It answers: "Who is in this room RIGHT NOW?"
                   It becomes NULL on checkout.

ORDER / ACTIVITY BOOKING LINKS:
┌──────────────────────────────────────┐
│            orders                    │
│ room_id    UUID FK → rooms.id        │ ← Static: which room ordered
│ guest_id   UUID FK → guests.id ◄──── │ ← Set at create time via current_guest_id lookup
└──────────────────────────────────────┘
current_guest_id
The live pointer. Changes on every check-in and check-out. Answers "who is in Room 302 right now." Used by create_order and book_activity_slot to auto-link charges to the active guest.
guests.room_id
The historical link. Never changes after check-in. Answers "which room did this guest stay in." Used for historical folio queries long after checkout.
orders.guest_id
Set at order creation time by looking up rooms.current_guest_id. This snapshot means even if the guest checks out mid-day, the order is still correctly attributed to them forever.
02 · Room-Guest Binding

Check-In Algorithm — Every Database State Change

A guest check-in triggers a precise sequence of database writes. All writes happen in a single transaction — if any step fails, all changes roll back and the room stays unoccupied.

1

Pre-flight validation

Before writing anything, the RPC checks:

  • Room exists — SELECT id FROM rooms WHERE room_number = '302' AND resort_id = [id]
  • Room is not occupied — WHERE is_occupied = false. If occupied: return error ROOM_ALREADY_OCCUPIED
  • Phone number format — basic regex validation, must be 10 digits
  • Caller is staff — RLS ensures only authenticated staff can call check_in_guest
READ: rooms (validation only — no writes yet)
2

INSERT into guests table

The guest record is created with status='checked_in'. The room_id is set here and never changes — it is the permanent historical link.

SQLcheck_out_guest RPC — all writes in one transaction
CREATE OR REPLACE FUNCTION check_out_guest(
  p_guest_id  UUID,
  p_folio_total INTEGER  -- passed from frontend for audit
)
RETURNS JSONB LANGUAGE plpgsql AS $$
DECLARE
  v_room_id UUID;
BEGIN
  -- Get room_id from guest record
  SELECT room_id INTO v_room_id
  FROM guests WHERE id = p_guest_id;

  -- ① Snapshot the folio total at checkout time
  INSERT INTO guest_folio_snapshots(
    guest_id, total_amount, snapshot_at, checked_out_by
  ) VALUES(
    p_guest_id, p_folio_total, now(), auth.uid()
  );

  -- ② Mark guest as checked out
  UPDATE guests
  SET
    status          = 'checked_out',
    actual_checkout = now()
  WHERE id = p_guest_id;

  -- ③ FREE THE ROOM — the critical step
  UPDATE rooms
  SET
    is_occupied      = false,
    current_guest_id = NULL   -- pointer cleared — room is available again
  WHERE id = v_room_id;

  -- ④ WhatsApp checkout message fires via trigger on guests UPDATE
  -- (trigger checks OLD.status='checked_in' AND NEW.status='checked_out')

  RETURN jsonb_build_object(
    'success',     true,
    'checked_out_at', now(),
    'room_freed',  v_room_id
  );
END;
$$;

ScenarioHow System Handles It

Any pending activity bookings for future dates are automatically cancelled (a trigger sets status='cancelled' on activity_bookings WHERE guest_id=X AND booking_date > actual_checkout AND status IN ('pending','confirmed')). Guest receives checkout WhatsApp.

Guest orders food before QR scan links room If a guest calls the reception and orders verbally before scanning QR, the receptionist creates the order manually in the Reception app. They select the room from a dropdown — the create_order RPC auto-links to the guest via current_guest_id lookup.
Walk-in diner (not a hotel guest) Walk-in diners at the Panache restaurant are not in the guests table. Their order has service_type='dine_in', table_id populated, and guest_id=NULL. Power cut / system offline mid-stay PostgreSQL ACID properties ensure no partial state. If the check-in INSERT succeeds but the rooms UPDATE fails, the transaction rolls back — room stays unoccupied, no orphan guest record. When system comes back online, receptionist re-runs check-in normally.
03 · Food Order Guest Linking

How Every Food Order Finds Its Guest

When a guest submits a food order, they type their room number. The create_order RPC uses that room number to instantly resolve the active guest. This means the guest never has to identify themselves — the room does it for them.

SQLThe room→guest resolution inside create_order RPC
-- STEP 1: Resolve room_id and current guest from room number
SELECT
  r.id                 AS room_id,
  r.current_guest_id   AS guest_id   -- The live pointer
INTO v_room_id, v_guest_id
FROM rooms r
WHERE
  r.resort_id   = p_resort_id
  AND r.room_number = p_room_number;

-- Three possible outcomes:

-- A) Room found, is_occupied=true, current_guest_id is set
--    → v_guest_id = 'gst-uuid-001'  (Rajesh Kumar)
--    → ORDER LINKED TO RAJESH: orders.guest_id = 'gst-uuid-001'

-- B) Room found, is_occupied=false, current_guest_id = NULL
--    → v_guest_id = NULL
--    → Order created with guest_id=NULL (walk-in or unregistered guest)
--    → Reception can manually link later via fix_order_guest(order_id, guest_id)

-- C) Room number not found in rooms table
--    → No row in result
--    → Order created with room_id=NULL, guest_id=NULL
--    → Guest typed a wrong room number — still processes, kitchen still sees it

-- STEP 2: Insert the order with resolved IDs
INSERT INTO orders(
  order_number, resort_id,
  guest_id,    -- May be NULL — that's OK
  room_id,     -- May be NULL — that's OK
  service_type, guest_name, guest_phone, items, subtotal, special_note
) VALUES(
  v_order_number, p_resort_id,
  v_guest_id, v_room_id,
  p_service_type, p_guest_name, p_guest_phone,
  p_items, p_subtotal, p_special_note
);
✅

Why the order always goes through even with NULL guest_id

The kitchen doesn't need a guest_id to prepare food. They need: what items, how many, which room/table. The guest_id is purely for billing attribution. An order with guest_id=NULL still appears on the Kitchen Panel immediately via Realtime. The reception can manually link it later using UPDATE orders SET guest_id='...' WHERE id='...' if needed. This ensures no order is ever blocked due to a database lookup issue.

CREATE OR REPLACE FUNCTION fix_order_guest(
  p_order_id UUID,
  p_guest_id UUID
)
RETURNS VOID LANGUAGE plpgsql AS $$
BEGIN
  -- Only owner/receptionist can call this (enforced by RLS)

  SET guest_id = p_guest_id

04 · Activity Booking Linking

Activity Booking → Guest Identity Algorithm

Activity bookings follow the same room-lookup pattern as food orders, with one additional layer: stay-date validation. The system checks that the booking date falls within the guest's actual stay.

SQLGuest resolution + stay validation inside book_activity_slot RPC
-- Inside book_activity_slot, after capacity check passes:

-- STEP 7A: Resolve room and guest from room_number
IF p_room_number IS NOT NULL THEN
  SELECT
    r.id,
    r.current_guest_id,
    g.check_in_date,
    g.expected_checkout
  INTO v_room_id, v_guest_id, v_checkin, v_checkout
  FROM rooms r
  LEFT JOIN guests g ON r.current_guest_id = g.id
  WHERE r.room_number = p_room_number;

  -- STEP 7B: Stay date validation
  -- Booking date must be within the guest's stay window
  IF v_guest_id IS NOT NULL THEN
    IF p_booking_date < v_checkin OR p_booking_date > v_checkout THEN
      RETURN jsonb_build_object(
        'success', false,
        'error',   'BOOKING_OUTSIDE_STAY',
        'message', 'Booking date is outside your stay dates.'
      );
    END IF;
  END IF;
END IF;

-- STEP 7C: For requires_balcony activities, verify room has balcony
IF v_activity_requires_balcony AND v_room_id IS NOT NULL THEN
  IF NOT (SELECT has_balcony FROM rooms WHERE id = v_room_id) THEN
    RETURN jsonb_build_object(
      'success', false,
      'error',   'NO_BALCONY',
      'message', 'This activity requires a room with a balcony.'
    );
  END IF;
END IF;

05 · Security Model

Defense in Depth — All Security Layers

Security in this system is not a single gate — it's five independent layers. Even if one layer is bypassed, the others prevent damage. This is the standard approach for production systems handling personal and financial data.

Layer 1 — Network & Transport
All three apps served over HTTPS (TLS 1.2+) enforced by Vercel. Supabase API only accessible over HTTPS. No HTTP fallback. HSTS headers configured. Certificate auto-renewal via Let's Encrypt.

What this prevents: Man-in-the-middle attacks, data interception in transit, credential sniffing.
Layer 2 — API Key Separation
Anon key — public, in browser JavaScript. Limited by RLS to read-only menu data, insert-only orders. Cannot read guest records.

Service role key — bypasses RLS. Lives only in Supabase Edge Functions and the database config. Never in browser code, never in frontend env vars.

What this prevents: Even if someone extracts the anon key from the JS bundle, they can only do what RLS allows — browse the menu and place orders.
Layer 3 — Row Level Security (PostgreSQL)
Every table has RLS enabled with an explicit deny-all default. Policies grant minimum required access per role. Anon sessions cannot read guests, staff, analytics, or folios. Authenticated sessions are scoped to their resort_id.

What this prevents: Even direct Supabase REST API calls with the anon key cannot access protected data — the database itself enforces the access rules.
Layer 4 — Function-Level Guards (SECURITY DEFINER)
RPCs that need elevated access (create_staff_account, verify_staff_pin, check_in_guest) use SECURITY DEFINER with explicit role checks at the top. They verify the caller's role before doing anything. This means calling the function directly via the API with a kitchen staff JWT cannot execute owner-only actions.

What this prevents: Privilege escalation — a kitchen staff account cannot call the owner-only functions even if they know the function name.
Layer 5 — Rate Limiting & Lockouts
Supabase Auth has built-in rate limiting on auth endpoints. PIN login has 3-attempt lockout (30 seconds) + cumulative 10-attempt lockout (owner unlock required). API calls are rate-limited by Supabase at the infrastructure level.

What this prevents: Brute force attacks on PINs, credential stuffing attacks, API abuse.
Layer 6 — Complete Audit Trail
Every sensitive action is logged: staff creation, PIN changes, login attempts, check-ins, check-outs, order guest re-linking, manual price overrides, menu changes. The audit log is append-only — no RLS policy permits deletion.

What this provides: Full forensic capability for disputes, reconciliation, and security incident investigation.

Algorithm & Function Reference

Algorithm / FunctionWhere UsedWhat It DoesCritical Property
bcrypt (work factor 12) PIN hashing on create, verification on login Converts 4-digit PIN to 60-char irreversible hash. Self-salted — unique hash every time even for same PIN. ~300ms per verify — brute force of 10,000 PINs takes 50 min per hash
JWT RS256 Supabase Auth — all staff sessions Asymmetrically signed token carrying role and user_id. Supabase verifies signature on every API call. 1-hour access token + 7-day refresh. Auto-refreshed by SDK.
pg_advisory_xact_lock book_activity_slot RPC Acquires an integer-keyed lock scoped to the current transaction. All concurrent bookings for same slot+date queue up. Lock auto-released on transaction commit/rollback. Cannot deadlock with itself.
current_guest_id pointer create_order + book_activity_slot RPCs Live FK on rooms table pointing to the currently checked-in guest. Enables zero-effort guest attribution for all orders. Set on check-in, cleared on check-out. NULL = room unoccupied.
UNION ALL VIEW (guest_folio) Reception folio panel + checkout Combines food orders and activity bookings into one chronological ledger. Computed at query time — always current. No stored state — reflects real-time. New order = instantly on folio.
Date range intersection Slot booking validation in book_activity_slot Ensures booking_date falls within guest's check_in_date → expected_checkout range. Prevents booking activities for days outside the stay.
SUM(number_of_guests) availability get_available_slots RPC Counts people (not bookings) against slot capacity. Prevents overbooking when one booking covers multiple guests. Excludes cancelled + no_show status from count.
